# 12.5 O(1) vs só r.on

> **TL;DR**
> `r.on` desce a árvore na ordem que você escreveu. `hash_routes` olha o primeiro segmento num Hash e salta para o ramo. Dezenas de prefixos não pagam varredura linear. O bloco **dentro** do ramo continua árvore.

## A árvore da A

**O que é:**
`r.on "eventos"` então `r.on "locais"` então `r.on "lotes"`... Cada request tenta até casar.

**Como funciona:**
Dois ramos: irrelevante. Cinquenta: ainda rápido em Ruby. O ponto não é microbenchmark. É **organização** + lookup direto. A entrevista puxa O(1) — você fala: Hash key, não regex na lista Rails.

**Na entrevista:**
> "on é sequência. hash_routes é chave. Cinquenta prefixos eu não empilho on. Eu registro branch."

---

## O Hash da B

**O que é:**
Primeiro segmento → bloco. O(1) amortizado. Sem varrer 49 `on` que não casam.

**Como funciona:**
`/eventos/1` → chave `eventos` → bloco de eventos.rb → `r.on Integer`. O Integer ainda é árvore. O(1) é o **despacho do módulo**, não o id.

**Na entrevista:**
> "O(1) no prefixo. O id continua matcher. Eu não vendo O(1) no CRUD inteiro."

---

## O que não muda

**O que é:**
halt, dataset, JWT, json plugin.

**Como funciona:**
B não é outro framework. É o mesmo Roda partido. Quem sabe A lê B em cinco minutos.

**Na entrevista:**
> "B não troca a stack. Troca o arquivo. O fio HTTP é o mesmo."

---

## Recapitulando

- on = ordem
- hash_routes = chave
- O(1) no módulo
- árvore dentro do ramo
