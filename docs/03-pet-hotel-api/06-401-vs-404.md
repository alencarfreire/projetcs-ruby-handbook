# 3.6 Recorte por user: 401 vs 404

> **TL;DR**
> 401 é “eu não sei quem você é”. 404 é “esse recurso não é seu — e eu não confirmo que existe”. Ana com token válido pedindo o owner da Maria (do João) leva 404, não 403. Sem token, 401. O `find` no `current_user.owners` faz o recorte. Pundit não entra.

## Três pessoas no quadro

**O que é:**
João opera a pousada. Maria é dona do Thor. Ana é outra recepção, outro User. Ana não vê a Maria.

**Como funciona:**
Dois users no banco. Cada um com seu `api_token`. O path `/api/v1/owners/:id` não tem o user. O token decide. Sem isso, você enumera ids.

**Quando usar:**
Qualquer API com mais de um user. Take-home que esquece isso vazou o hotel da Ana.

**Na entrevista:**
> "O id na URL não autoriza. O token autoriza. Eu busco no current_user.owners, não em Owner.find."

## 401 identidade

**O que é:**
O servidor não autenticou. Header sumiu, Bearer lixo, token regenerado no logout.

**Como funciona:**
`require_login` no pai. Todo controller herda. Signup e login dão `skip_before_action`. Occupancy não dá skip.

Body: `{ "errors": ["token ausente ou inválido"] }`. Uma frase. Sem “token expirado” — este token não expira. Sem “user não encontrado”.

**Exemplo prático:**
Logout regenera. O curl seguinte com o token velho: 401. Não 404. Você ainda não chegou no recurso.

**Na entrevista:**
> "401 antes de olhar o id. Eu não busco o owner se eu não sei o user."

## 404 recorte

**O que é:**
Identidade ok. Recurso não. Id inexistente **ou** id de outro user. Os dois são 404.

**Como funciona:**

```ruby
def set_owner
  @owner = current_user.owners.find(params[:id])
end
```

`Owner.find` acharia a Maria da Ana. `current_user.owners.find` não acha. `RecordNotFound`. 404.

O spec:

```ruby
get "/api/v1/owners/#{maria.id}", headers: auth_headers(ana), as: :json
expect(response).to have_http_status(:not_found)
```

Ana está autenticada. 401 seria mentira. 404 é o recorte.

**Quando usar:**
Sempre que o recurso pertence ao user. Stay, pet, owner. Occupancy já vem filtrada — não tem id na URL.

**Na entrevista:**
> "404 no recurso alheio. Eu não confirmo que o id 7 existe no hotel do João."

## Por que não 403

**O que é:**
403 diz “eu sei que existe e você não pode”. É informação. Enumeração de ids vira mapa do hotel alheio.

**Como funciona:**
Pundit costuma 403. Recorte daqui: não Pundit, não 403. O `find` encadeado transforma “não autorizado” em “não encontrado”. Mentira útil.

Se a vaga pede 403 e policy, você fala: “em produção Pundit; neste take-home o scope do Active Record”.

**Na entrevista:**
> "403 entrega que o id existe. 404 não. API pública de id sequencial agradece o 404."

---

## O find encadeado

**O que é:**
A cerca. `current_user.stays.find`. `current_user.pets.find`. Igual o HTML do 2.

**Como funciona:**
`belongs_to :user` em tudo. Create usa `current_user.owners.new`. O `user_id` não vem do JSON.

Pet ainda valida `owner_belongs_to_same_user`. Ana não cola o `owner_id` da Maria e cria o Bidu no hotel dela — 422.

**Exemplo prático:**
Ana autenticada. POST pet com `owner_id` da Maria. Model recusa. 422. Não 404 — o create não faz find do pet. A validação de owner cobre.

**Na entrevista:**
> "find encadeado no show. validação de owner no create. Os dois recortes. Um não substitui o outro."

## rescue_from

**O que é:**
O `find` explode `ActiveRecord::RecordNotFound`. Sem rescue, 500. Com rescue, 404 JSON.

**Como funciona:**

```ruby
rescue_from ActiveRecord::RecordNotFound, with: :render_not_found

def render_not_found
  render json: { errors: ["não encontrado"] }, status: :not_found
end
```

Mensagem genérica. Não `Couldn't find Owner with id=7`. A default do Rails vaza o model e o id.

**Quando usar:**
API JSON, sempre. HTML do 2 já tinha página 404. JSON precisa do body.

**Na entrevista:**
> "rescue_from no pai. Mensagem genérica. Eu não vazoo o nome da tabela no 404."

## Recapitulando

- 401 = sem identidade
- 404 = recurso fora do scope
- 403 não entra: entrega existência
- `current_user.owners.find`, nunca `Owner.find`
- rescue_from para não 500

## Exercícios práticos

### Exercício 1: Occupancy da Ana

**Enunciado:** Thor está checked_in no hotel do João. Ana chama `GET /api/v1/occupancy` com o token dela. O que volta?

<details>
<summary>Solução</summary>

200 e `[]`. Não 401 — ela está autenticada. Não 404 — occupancy não tem id. A lista é do `current_user`. Thor não é dela. Array vazio é o recorte correto, não um erro.

**Pontos-chave:**
- 200 vazio ≠ 404
- filtro no user, não no status HTTP
- occupancy não vaza o Thor
</details>

### Exercício 2: Owner.find

**Enunciado:** Você escreveu `@owner = Owner.find(params[:id])` e “autoriza depois”. O que o entrevistador faz?

<details>
<summary>Solução</summary>

Pede o token da Ana e o id da Maria. Se o “depois” esqueceu, vazou. Se o depois é 403, enumerou. O find encadeado não tem “depois”. A query já é o recorte.

**Pontos-chave:**
- scope na query
- after_action de authorize chega tarde
- id sequencial + find global = mapa
</details>
